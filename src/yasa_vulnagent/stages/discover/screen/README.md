# screen

screen consists of an outer LangGraph node and a recoverable task subgraph. The outer node handles the initial three views, wave scheduling, deduplication, ledger persistence, and result merging. The task subgraph always runs through `prepare_context → analyze → validate → persist`, and its model loop may use read-only tools only.

The initial wave creates three isolated tasks: `component-runtime`, `input-boundary`, and `independent-exploration`. They all reference the same ledger-backed production-text scope, so the task records do not copy its paths. Initial tasks are exploratory and may finish without closing every file. Actual read receipts accumulate per file. Candidates are merged only after each task attempt is committed.

After the initial wave, `planner.py` builds a compact ledger-derived repo map and work board, selects existing pending tasks first, and may propose at most two bounded new screen tasks per wave. The work board's `priority_hints` are model ordering suggestions derived from source-role candidates, confirmed source entries, mechanism hits, and prior attempts; they are not deterministic sorting or coverage evidence. Planner proposals must be grounded in unread files, open follow-ups, or candidate entries, and are validated before task creation. Planner failure records a warning and creates no fallback tasks. The planner never reads source text. Each wave shares time and model-call budgets; tasks do not receive independent quotas.

Source tools include inventory-scoped `list_directory`, `glob`, `search_text`, and `read_file` with line-range and character limits. Directory, glob, and text-search results use stable cursors; continue pagination instead of assuming a truncated page is complete. Each task receives a ledger-backed scope reference rather than a full path list, and path authorization is checked by SQLite. YASA MCP exposes only `search_symbol`, `get_function`, `get_class_by_name`, and `get_import_by_file`, with a fixed project path and bounded result sizes. When YASA fails, its receipt is retained and source reading is used as a fallback; structural navigation results are not semantic evidence by themselves.

After a task commits, screen processes any structured `feature_observations`. The shared feature service validates the observation's source-backed definition and same-task read receipt, stores one canonical mechanism, runs a bounded query over ledger-authorized production text, and materializes deduplicated hits as candidate entries and file-scoped confirm tasks. Query results and confirm reads do not create read receipts, so they do not make a file screened. A candidate from screen is a lead, not a confirmed entry.

Completed screen tasks may return structured `follow_up` and `deferred_items`; screen creates deduplicated follow-up screen tasks and records the rest for review. Candidate entries from screen are scheduled for confirm, and coverage remains open until a screen task has complete read receipts or review accepts an explicit disposition.

Each task writes its `read_ranges`, tool receipts, candidates, negative results, unknown/deferred items, feature observations, and follow-ups to `screen/tasks/<task_id>.json`. Runtime models and MCP sessions are not stored in `DiscoverState`; `prepare` requeues running tasks after an interruption. A completed artifact restored from disk is committed through `commit_task` so receipts, candidates, coverage, and evidence are not lost. Feature observations and follow-ups left unprocessed by an interrupted commit are replayed on the next screen pass; `derived_processed` prevents already-handled work from being replayed again. Missing API keys or MCP never produce a fabricated completion; tasks remain pending/partial and record the gaps.
